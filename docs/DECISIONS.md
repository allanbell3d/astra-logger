# ASTRA decisions

Status: canonical MVP target contract; implementation acceptance remains open.

## Status and purpose

This document records the product and operating decisions that should guide ASTRA's next small, working version. It is a specification of the intended behavior, not a claim that the current runtime implements it or that paused schedules may resume. The logger and decision flow are independent per host and OS-agnostic; Hermes provides the existing scheduling and agent integration. The goal is to preserve health evidence, make known problems quiet but visible, escalate genuine new problems, avoid paying for the same investigation without meaningful new evidence, and keep necessary repair work from being forgotten.

Only an explicit owner decision authorizes a new feature, storage schema, service, framework, model change, live deployment, or schedule change. Prior proposals and isolated tests do not enlarge that authority. [REQUIREMENTS.md](REQUIREMENTS.md), [SPECIFICATIONS.md](SPECIFICATIONS.md), and [ACCEPTANCE.md](ACCEPTANCE.md) describe the contract and proof in more detail.

## Evidence and decisions are different kinds of data

Capture and enrichment must preserve what happened. Enriched observations remain lossless and append-only until an explicit store retention policy expires them. Similar text must not collapse different resources, journal cursors, file rotations, timestamps, events, findings, retries, investigations, lanes, or publication attempts. A decision may add classification, counts, diagnosis, report paths, delivery records, and repair status, but it must not rewrite an observation to fit a later interpretation. Capture should keep running when an LLM, provider, delivery destination, or scheduler step fails; inference is downstream of durable evidence.

Use the terms consistently. A severity label comes from configured policy and describes the signal, such as `ignore`, `watch`, `needs-attention`, or `tracked`. Triage disposition answers what to do with a particular finding. RCA records an investigation result. `diagnosed_unrepaired` means a cause was established but no repair was made; `investigation_inconclusive` means the symptom is real but the cause is unproven; `verified_fixed` requires a performed repair and later relevant verification. `informational` records an expected or nonactionable fact. A completed RCA, a published report, and a fixed problem are three different outcomes. Minimum status tracking must retain in-progress, unresolved, and fixed work, along with lease and delivery state sufficient to recover interrupted work. Simplicity is a constraint on how this is built, not a reason to discard that necessary state.

Daily output should count recurring known and watched issues and show their latest condition without generating a new investigation or notice on every occurrence. Notices should be brief, actionable, and deduplicated by notice state. A substantive change in notice state can create a new notice; presentation-only wording changes must not manufacture an alert; the send ledger should mark a notice sent only after successful delivery. Notice deduplication alone does not stop repeated RCA, so investigation eligibility needs its own rule. Severity labels, investigation priority, owner action, and repair status must stay separate. Models and severity belong to operator configuration, not hardcoded engine choices.

## Triage and RCA work

Triage is a free configured production escalation decision over the exact bounded batch it was given. Every leased finding ID must receive exactly one allowed disposition and a short evidence-based reason. Completion must reject missing, extra, duplicate, unknown, or malformed IDs rather than silently completing partial work. A compact result skeleton and capped, specific error feedback can help an agent correct a submission in the same lease. Global backlog counts are not the leased batch size; evidence hashes are not finding IDs. Failed attempts must be bounded and visible. A blocked batch is unfinished work, not an accepted result, and recovery must preserve its membership and reason. Recovery should release only retained, unfinished evidence; expired evidence cannot be silently presented as a fresh investigation. There is no blanket mass requeue.

For the MVP, RCA begins from an approved triage outcome. A direct urgent bypass is deferred; existing detection may prioritize triage but must not purchase RCA before its validated decision. Its worker may inspect the relevant evidence, prior diagnosis, and bounded read-only state for the affected resource. It does not repair hosts, restart services, edit credentials, change schedules, or switch providers. A report with an established cause records the evidence and relevant alternatives ruled out. If the cause cannot be established, it says so and identifies the next useful check. Repeated tool failure or diagnostic command output from the RCA worker must not automatically become a new source-system defect. Report completion consumes the investigation; repair status stays separate.

Persisting diagnosis and its scoped relationship in the existing `rca_investigations`/`rca_coverage` tracking is accepted required behavior, not an open choice about adopting those tables. Reuse existing methods and correct demonstrated behavior gaps; further physical storage additions need their applicable authority. Prior diagnosis can avoid another RCA only when it is complete, in scope, and accessible. At the new investigation's creation time, the prior diagnosis must already have completed and its report must be present in the applicable preserved evidence set. Event time and later publication time do not substitute for that decision time. A matching sentence or provider-generated relationship is not sufficient. Count and link recurrences while retaining the underlying evidence. Missing publication calls for delivery recovery; it does not by itself justify rerunning RCA. When essential evidence has expired, say that the basis for a decision is unavailable rather than inventing a cause or quietly suppressing work. A bounded RCA run may investigate multiple eligible findings, including unrelated errors. Sharing a batch does not assert a common cause: every member retains its own diagnostic outcome and report attribution, and overflow remains pending. Sharing a diagnosis or coverage across findings still requires explicit evidence of the same scoped incident or cause; distinct resources and causes remain distinct.

Material new evidence, a new cause/event class, a different affected resource or diagnostic scope, changed impact, and recurrence after verified repair may reopen a diagnosed issue. The never-repeat rule applies to an unchanged known issue; it does not prohibit this evidence-based material-change exception. Record the reopening basis and require validated triage before RCA. Frequency-only reopening is deferred beyond the MVP: count and report increases, but require a material change in evidence, scope, impact or verified-repair context before another diagnosis. A new message that merely resembles an old one must not be automatically suppressed, and a familiar message with a new mechanism must not be hidden by the old diagnosis. The resulting rule must be deterministic, explainable and testable against known repeats and counterexamples before it controls paid work.

## Independent comparison lanes

The ordinary operating shape uses one RCA lane. A second lane may be enabled for a specific model comparison or second opinion; it must be independently deactivatable. When B is closed, no new B leases or launches are allowed; preserve B history. Disabling B is not a mid-task cancellation: an already running investigation may finish, but no new B work launches. When B is enabled, it applies only to new work arriving after enablement; older waiting, already-started and completed investigations are not automatically assigned to it. When two lanes are open, both receive the exact same evidence and findings. They keep separate completion flags, archives, publication paths, and delivery outcomes. They are independent model comparison outputs, not a consensus vote or two replicas whose agreement is required to finish ordinary work. One adequate RCA can complete the ordinary investigation; the mere absence of a B report must not reopen it.

The target supports independently configured model choices for lanes that are open. The exact configuration and phase mechanism for those choices is an implementation question tracked in [TODO](../TODO.md), not an open question about whether optional B is allowed. Engine code should apply the operator's selected model playbook without silently pinning, substituting, or adding fallback models. Any phase configuration swap must preserve untouched text byte-for-byte and restore exactly; reserializing the whole YAML file is unsuitable because it can alter quoting and wrapped values. Lane isolation occurs at writes and delivery, not by feeding lanes different inputs.

## Delivery and operation

HTML is the required format for every human report, including RCA, closure and daily-review reports when produced. Human access must support a direct HTML link or downloadable HTML without private-network access. A configured publication destination is optional; when its link is unavailable to the recipient, deliver downloadable HTML through the configured native route. Markdown may remain an internal source/archive representation but is not the human-delivery fallback.

A report is persisted when its accepted original is durably retained. It is published when its configured destination is verified available. A notification is delivered when the native route records a successful send. These are separate facts. A native attachment may deliver the report without a separate publication destination. A local archive, a short pointer, a scheduler success flag, and a worker's unsupported claim are not delivery proof. Failures remain visible as delivery work and recover from the retained report. Any change to the existing partial delivery implementation should address a demonstrated gap in these outcomes, using working mechanisms first.

Keep the existing native Hermes cron cards, one-shot RCA behavior, and explicit rearm with a future time. Consuming a one-shot card does not make a plain resume sufficient if its original time is in the past. Schedules stay under operator control. Deployment, enabling or resuming schedules, and paid investigations are distinct acts. Production should not be used to discover whether a proposed design works; prove the approved flow on isolated state first. A current full test run is required before deployment, followed by backed-up synchronization and verification where deployment is separately authorized.

Troubleshooting should preserve distinctions. A route permission error differs from authentication failure; rate or quota error does not establish empty credit; missing optional credentials do not prove billing failure; JSON validation refusal is not necessarily policy refusal. Inspect the exact route, runtime attempts, and sender identity before assigning cause. Preserve corrupt store bytes and diagnose writers before repair. Historical snapshots do not certify the live system now.

## Model, alert and operator-action decisions

Steady-state triage is intended to have zero model cost and use free configured models. During the first few weeks of initial tuning, different models, including inexpensive paid models, may be compared to improve tagging, filtering, packet context and the workflow toward results achievable with free models. This is a temporary tuning allowance, not a permanent paid-triage default or automatic fallback. The exact candidate-admission rule is implementation/tuning work alongside the other repairs, not a documentation blocker or a settled choice to review every new finding. RCA needs capable, low-cost reasoning and must not be assigned free/lightweight triage models. Pick routes in configuration and verify actual primary, auxiliary and fallback use. A failed route must stop within its bounds instead of silently escalating spend. Contributor tasks use models suited to their complexity under contributor guidance; this is independent of product scheduled-job policy.

Immediate incident notifications are strictly for genuinely new failure signatures or critical service routing outages. Known repeats and routine incidents are counted deterministically and combined into one compact daily balance. Notices contain one or two short sentences and point to the retained HTML report where a report is required; do not dump multi-page Markdown, raw JSON or logs. The notice ledger records successful sends and survives restarts. This alert rule governs incident alerts. Requested responses, report delivery and repair/closure notifications remain separately required when their workflow calls for them; recovery must reuse the same report identity.

Operator actions such as deliberately changing channel permissions are not autonomous system-failure triggers. Record expected behavior and transient non-failures, retain counts, and distinguish restricted unauthorized destinations from the instance's approved report/service routes. Critical routing outages remain eligible for mandatory triage. A blanket exemption for every 403 or 429 would hide real incidents and is not accepted.

The operator should be able to review a trustworthy diagnosis and take one simple authorized action. That convenience goal does not approve new repair tooling or unattended execution. A safe repair can run automatically only when the exact repair path has been explicitly pre-approved; other repairs require owner action or authority. Failed attempts are recorded and verified rather than endlessly repeated.

## Confirmed MVP policy

- **Multi-finding RCA is allowed.** A bounded investigation may cover unrelated eligible errors; relatedness is not an admission requirement. Account for every member separately, retain pending overflow, and never infer a shared cause merely from one batch/report.
- **Urgent bypass is deferred.** All MVP RCA requires validated triage. A future bypass would need explicitly agreed signals, authority and spend limits; do not build it now.
- **Frequency-only reopening is deferred.** Keep recurrence counts/reporting. More occurrences alone do not reopen an otherwise unchanged diagnosis in the MVP.
- **B is not stopped mid-task.** Closing B prevents new launches while an already running investigation finishes and retains its result/history.
- **Long-term archive policy is deferred.** Retain RCA reports and add no automatic archive deletion in the MVP. The existing active-evidence window remains separate; retention automation is future work, not a prerequisite for getting the logger working.

## B activation and clean commissioning

B applies only to new work arriving after it is enabled. Do not add an MVP backlog-selection/backfill feature or automatically assign historical pending, active or completed investigations to B. Use the simplest existing configuration/time boundary that satisfies this behavior.

A clean start may be proposed for commissioning instead of processing historical backlog. Inspect the exact configured work/log roots, review state, cursor behavior and pending native jobs first; clearing logs alone is not necessarily a clean review state. Prefer a fresh configured work root where suitable. Any deletion or live-state reset requires explicit approval of its exact scope; this decision does not itself authorize wiping files or changing jobs.


Implementation, host activation, and schedule resume follow their own explicit owner decisions. The immediate proof target is a known repeat that does not relaunch paid RCA, a genuinely new or materially changed issue that does, visible failed/expired work, a Lane A run, an optional opened and closed Lane B, a retained retrievable report, and verified native delivery. Verify publication separately when it is configured.

## Script tagging and LLM judgment

Initial classification and severity tagging are performed by scripts and configured policy. The LLM is present to exercise judgment over the supplied bounded evidence, notice when script tags are wrong, and handle scenarios the scripts did not anticipate. It chooses the appropriate supported triage disposition and gives an evidence-grounded reason explaining a discrepancy or consequential uncertainty. This does not make the LLM an unrestricted investigator and does not let a severity label bypass mandatory triage.

Preserve the original script classification/severity and provenance. Notice/decision output must distinguish the script's label from the LLM's judgment; do not rewrite the original observation, mutate severity policy, or silently add persistent override fields. Inspect the existing supported result/reason mechanism first. A new persistent override representation, if actually required, needs its explicit contract and applicable approval. These distinctions settle the script-first/LLM-judgment policy without claiming the current implementation already does it.
