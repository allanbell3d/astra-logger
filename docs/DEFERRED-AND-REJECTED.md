# ASTRA deferred and rejected approaches

Status: canonical MVP target contract; implementation acceptance remains open.

## How to read this register

This register protects the small operational goal in [DECISIONS.md](DECISIONS.md). “Rejected” means an approach should not be revived as the default or executed under present authority. “Deferred” means the problem or proposal may deserve a later owner decision, but is not approved implementation work now. Facts learned while evaluating an approach remain useful evidence; an old plan, completed analysis, or artifact on disk does not authorize its program. This register does not demote required evidence retention, exact finding coverage, recurrence accounting, delivery proof, or minimal investigation and repair status into optional extras.

## Rejected as operating or execution approaches

- **DR1 — A broad takeover program or a single all-purpose repair prompt.** A large phase list, exhaustive matrices, new policy catalogs, and blanket acceptance criteria would obscure the next working result. A task must keep its explicit scope and applicable authority; a rejected execution program does not prescribe the implementation sequence for every task. A defect from an older plan may be addressed in a bounded approved task, without adopting the entire plan.
- **DR2 — Analyze-everything or undirected document mining.** Historical material should answer a defined question with deduplicated, grounded conclusions. Similar prose cannot erase distinct events, findings, retries, lanes, timestamps, or publications. Offline replay and agent completion markers do not authorize production behavior.
- **DR3 — Blind suppression of investigation.** Do not skip RCA because text looks similar, a prior report might exist, or a provider supplies a loose grouping. Reuse must account for evidence, scope, diagnosis completion time, preserved report access, and material change. An annotation-only replay cannot be silently promoted into paid-work suppression or claimed cost savings.
- **DR4 — Automatic host repair.** ASTRA can find, diagnose, count, report, and track work. Repair execution needs the owner's action or an explicit decision for the specific repair. A report, delivered message, or “done” marker does not prove a fix.
- **DR5 — Two RCA reports as a standing completion rule.** The optional second lane serves deliberate comparison or second opinion. It is not automatic consensus, compulsory redundancy, or a reason to reopen an otherwise complete investigation when B was closed.
- **DR6 — Mass unblock, mass requeue, or unlimited paid recovery.** A blocked batch retains unfinished work and requires an explained bounded recovery that checks evidence availability. Raw updates to the review store, automatic infinite retry loops, and bulk relaunch of stale investigations are unsuitable.
- **DR7 — Production launch as a design test.** Enabling cards or running paid investigations must not be the way to learn whether a new rule, schema, or delivery path works. Isolated representative proof comes first; deployment and schedule resume are separate owner decisions.
- **DR8 — Silent provider or model changes.** Do not hide failures with expensive fallback chains, pin models in engine code, or change provider routes to repair an unrelated exact-ID error. Model choice belongs to configuration. A rate/quota error is not proof of billing exhaustion.
- **DR9 — Replacing native scheduling or modifying Hermes core.** Existing cron cards and one-shot rearm remain the control surface. Do not replace eligibility-driven one-shot RCA with a recurring interval card to work around rearming. New schedulers, gateway workarounds, core patches, or general administration layers need a different explicitly approved problem and scope.
- **DR10 — Broad infrastructure or speculative architecture.** A new observability stack, control plane, accounting framework, extra database, general-purpose service, or platform rewrite is not justified by the immediate health-flow goal. New tables and expanded lifecycle models are not approved simply because an earlier partial implementation exists. Necessary minimum status remains required and should be delivered with existing mechanisms where possible.
- **DR11 — Unsafe repository or evidence cleanup.** Do not erase evidence, roll back a store, edit frozen historical plans, delete lane state, remove private archives incidentally, reset Git history in bulk, or commit credentials and runtime material. Exact deletion or archive sets need separate review. Do not claim portable/public readiness while paths, privacy boundaries, and tests are unresolved.

## Deferred choices and proposals

These require a new, specific owner decision before implementation or activation:

- **DF1 — Long-term RCA archive retention automation:** deferred until after the MVP works. Retain reports; add no automatic archive deletion. This does not change the established active-evidence window or authorize a cleanup job.
- **DF2 — Additional delivery infrastructure:** an alternative publisher, remote report server or expanded synchronization mechanism requires a demonstrated need and a separate scope. Required persistence, native delivery and minimal repair tracking remain core obligations; inspect and complete the existing path where it falls short. Activation on another host remains separate.
- **DF3 — Additional reuse algorithms or storage:** report-backed, scoped, deterministic reuse and the approved material-change exception are required behavior. An additional algorithm or storage proposal needs its own necessity and authority; do not defer the whole required reuse behavior while awaiting a new design. Necessary deduplication and status accounting are already product requirements; what remains deferred is the particular algorithm or storage change. Permanent diagnosis tracking and reuse of the existing `rca_investigations`/`rca_coverage` methods are accepted requirements. Historical standalone-candidate results did not establish deployment acceptance; they do not make current table reuse an open product choice. Further schema expansion needs a demonstrated gap and applicable approval.
- **DF4 — A direct urgent bypass and frequency-only reopening:** both are deferred beyond the MVP in [DECISIONS.md](DECISIONS.md). Keep urgent detection/triage priority and recurrence counts; do not implement their direct-launch or frequency-threshold frameworks now. Bounded multi-error RCA, including unrelated errors with separate outcomes, is accepted MVP work rather than a deferred grouping feature.
- **DF5 — Automatic matching from static known-issue notes:** the existing optional bounded context input is documented in Specifications. A static note alone is not persisted diagnostic coverage. Turning it into an automatic matcher that suppresses paid work would need an explicit contract and acceptance; it must not bypass report-backed scope and material-change checks.
- **DF6 — Convenience and fleet-level delivery tooling:** a generic skill, alternative publisher, or operator convenience layer can be proposed after the core flow works. It must not become a dependency of the immediate evidence, triage, RCA, delivery, and repair-status contract.
- **DF7 — Repository reorganization and public release:** possible work includes import/layout repairs, portable configuration, reviewed sample files, test/doc tracking, license and packaging, private-material exclusion, and a clean baseline strategy. Existing paths and historical inventory are not an approved move/delete list. Publication requires its own readiness and privacy review.
- **DF8 — Host cleanup, data migration, and schedule resume:** each needs an exact scope and owner decision. Backups and checksum verification protect an approved sync, but file sync never enables a schedule by implication. A successful isolated test, overnight run, or prior approval for a different host does not authorize a new deployment or paid run.

When revisiting a deferred or rejected approach, state the concrete operator problem, why the current smaller path cannot solve it, the smallest proposed change, its data/model/host/schedule effects, and how to reverse it. The owner can then decide that specific change without reopening an old program wholesale.

## Further excluded patterns and their preserved rationale

| ID | Approach and disposition | Why it is excluded / what remains required |
|---|---|---|
| DR12 | Relax exact finding-ID coverage, silently accept missing members, or mark a whole RCA batch complete from its first ID — rejected. | Throughput cannot trade away work accounting. Keep exact membership, bounded useful correction feedback, per-member outcomes and unrelated-work progress. |
| DR13 | Raise a dispatch timeout/turn cap without measuring the real failing path, or treat a fast microbenchmark as deadline proof — rejected. | Preserve the bounded 120-second triage acceptance target. Performance correction must preserve identity equivalence and lane isolation and demonstrate the actual representative path. |
| DR14 | Treat permission/rate/quota symptoms as automatic verified causes, blanket-suppress all 403/429 errors, or change models to hide them — rejected. | Distinguish deliberately restricted routes, missing credentials, provider codes, configured authorized routes and real outages. Expected owner actions are recorded; new failures still receive mandatory triage. |
| DR15 | Model ingestion of whole log trees, lengthy quiet runs, unbounded retries or fallback into expensive scheduled models — rejected. | Capture/counting are mechanical; quiet work makes no call. Steady-state triage is compact/free, RCA bounded and capable/low-cost. Initial tuning may temporarily compare inexpensive paid models to reach the free-model target; this does not permit unbounded sweeps or permanent expensive fallbacks. |
| DR16 | Collapse capture and enrichment into a slow recurring inference process or drop frequent “spam” evidence from JSONL — rejected. | Preserve original evidence and independent incremental mechanical capture. Frequency can change a compact view or deterministic counts, never justify deleting evidence. |
| DR17 | Treat weak relationship predicates, same finding ID or absent current-store evidence as suppression proof — rejected. | Distinct IDs can share a proven scoped cause; same text/ID need not. Judge reuse at investigation creation with prior completed/accessibly preserved diagnosis. Truncated evidence requires abstention; late reports cannot backdate eligibility. |
| DR18 | Remove unused native cards, lane state, backups or history without the exact reviewed scope — rejected as routine cleanup. | Preserve operator-visible control and useful evidence. A file sync or restored draft neither activates delivery nor resumes a schedule. |
| DR19 | Invent public environment variables, install commands, supported platforms or one-command unattended operation — rejected. | Public instructions must describe accepted interfaces with isolated caller-owned input and explicit store/lease side effects. Python source alone does not prove scheduler, shell, locking or service-adapter support. |
| DR20 | Claim deterministic execution while background model workers perform semantic tasks, report full-suite success from focused regressions, or accept a missing/timed-out review as PASS — rejected. | State actual execution, resource use, test/review limits and current evidence. Command success, DONE markers and retained artifacts do not establish acceptance or deployment. |
| DR21 | Recurring interval RCA cards, non-null native model pins overriding configured phase choice, or whole-YAML reserialization — rejected. | Use eligibility-driven native one-shot rearm and configuration-owned routing. A literal string `default` is still a pin; absent blocks remain byte-identical and restore uses the apply operation's saved bytes. |
| DF9 | Additional report publishing options — deferred. | Existing report/render/send mechanisms come first. Required direct HTML access/download and delivery proof are not deferred; an independently proposed convenience layer must not become a core dependency. The unsolicited portable delivery kit was explicitly rejected as unrequested work; it is not a deferred MVP component. New accounting/platform tooling remains outside the authorized goal. |
| DF10 | Live deployment/backfill or promotion of an offline replay rule set — not authorized by its artifact or test alone. | Preserve useful candidate work, counterexamples and measured annotation results. Existing persisted coverage and its current methods are accepted product work. An annotation replay is not paid-work suppression acceptance or authority for further schema expansion/live deployment/resume. Do not claim grouping arithmetic as billable calls or savings. |

Optional B, bounded multi-error RCA, minimum lifecycle state, required HTML and report/delivery recovery are accepted core behavior; do not reclassify them as rejected because implementation remains unfinished.
