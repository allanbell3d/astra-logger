# ASTRA acceptance evidence

Status: canonical MVP target contract; implementation acceptance remains open.

This document defines evidence that an implementation must produce before a requirement can be accepted. It makes no claim that the current implementation has passed any case. Use isolated fixtures, temporary work roots, and controlled native-job doubles for ordinary acceptance; do not enable schedules, send to a live destination, invoke models, or mutate a live store merely to document or run these cases.

Each case should record the input, observable result, retained state, and applicable requirement IDs. Focused cases establish a boundary; a representative chronological replay establishes that state transitions remain valid over time. Historical counts, screenshots, model output, and a successful process exit are not substitutes for this evidence.

## A. Capture, identity, and retention

**A1 — Crash and commit boundary.** Start with a source containing several complete records, interrupt capture between evidence append and cursor commit, then restart. The retained stream must contain each committed record once, no uncommitted record may be claimed consumed, and rebuilt projections must agree with committed evidence. Repeat after a second interruption to demonstrate idempotent recovery.

**A2 — File and journal identity.** Exercise file rotation, truncation below the saved offset, and overlapping configured source globs. A new file generation must be read without duplicating prior committed evidence; overlapping paths must yield one source. Separately use a journal record and verify that its cursor/unit/boot identity is retained without treating it as a file byte range. Provide naive runtime timestamps and journal microsecond timestamps to show source-local time interpretation and correct unit conversion.

**A3 — Malformed and incomplete input.** Place an incomplete final line and a malformed row after valid records. The cursor must remain at the unreadable boundary, the obstruction must be visible, and later content must not be silently declared consumed. Where continuation capture is clipped, the record must identify the clip rather than pretend it retained the full source.

**A4 — Independence and policy.** Make inference, credentials and notification unavailable and show capture still commits. Refuse an output or journal path that aliases an input. Apply first-match severity rules, change the policy, and rebuild projections without altering captured fields. Distinct hosts/profiles and affected resource paths must remain distinct; volatile presentation changes may group. Verify counts identify their units and original full evidence remains available behind a clipped sample.

**A5 — Collision, views, and lifecycle.** Give an input record fields that collide with ASTRA-owned enrichment fields. Prove original fields survive and pipeline values use the collision-safe location. Build grouped and compact views, filter one, and demonstrate the full evidence remains referenced and unacknowledged. Move evidence through active and archived storage, then exercise expiry of evidence needed by unresolved work: the work identity, disposition, history, and missing-evidence state must remain, while no blind RCA is created. State the configured retention rule; do not imply unlimited retention.

## B. Review, triage, and batches

**B1 — Store ownership and exact membership.** Prepare a batch with a known exact finding set and show that supported `ReviewStore` operations own its lease and acknowledgement. For every completion error—missing ID, extra ID, duplicate ID, unknown ID, wrong lane/batch, malformed field, and invalid decision—the batch and unresolved members must remain intact with a mechanical reason. A valid result contains exactly one decision per supplied ID and only `informational`, `watch`, `tracked`, or `rca`.

**B2 — Completion routing and history.** Send valid RCA report completions through the generic CLI for the supported RCA batch kinds, including A and B. They must reach lane-aware RCA accounting, not triage result parsing; the wrong result kind must not be accepted as successful review. Returned RCA history must preserve each report's lane identity, so comparison results remain distinguishable.

**B3 — Bounded triage.** Supply a packet at each relevant byte boundary, including the optional known-issues input and result template. Show the final packet stays within its specified cap, every display sample remains bounded, and the representative packet completes within the stated acceptance time. Instrument the triage environment to reject database access, extra evidence retrieval, browsing, repair, job/config edits, batch preparation, investigation, and independent sends. The valid result must use only supplied information and must not acknowledge a finding omitted for size.

**B4 — Finite attempts and isolation.** Lease a batch through its finite allowed attempts, include an invalid result and the permitted same-lease correction, then show exhausted work becomes visible and blocked. Targeted recovery must name that batch and preserve its earlier attempts. In the same fixture, show an unrelated eligible finding can proceed. A quiet/no-eligible case must return without a model request; queue age, delivery failure, or a successful native job alone must not create RCA eligibility.

**B5 — Exact worker output and completion limits.** Exercise 11-, 12-, 160- and 161-character triage reasons through the actual completion helper, along with a finding ID mistaken for an evidence hash and a duplicated result item. Valid results retain exact `id`/`decision`/`reason` membership and `status=reviewed`; invalid results consume no findings. Demonstrate useful capped missing/extra-ID feedback and a valid correction within the same allowed lease. On the representative maximum bounded packet, record elapsed time against the 60-second aim and 120-second ceiling. Quiet input returns `[SILENT]` and creates no provider request. A meaningful escalation brief obeys the two-line/350-character limit and uses only observed facts; a failed completion cannot claim acceptance or bypass store methods. These cases cover T2–T5 without authorizing a production model call.

**B6 — Script-first tagging and substantive LLM judgment.** Supply correctly tagged evidence, an incorrect script classification/severity, and an unforeseen scenario whose consequence the policy does not anticipate. Preserve original tags and provenance byte-for-byte. Triage must notice the error/limitation, use its supported decision/reason output to state evidence-grounded judgment, and choose the appropriate disposition, including warranted RCA after exact validation. It must not rubber-stamp tags, invent cause, rewrite the observation/policy or fetch extra evidence. Demonstrate the existing output mechanism before proposing a persistent override schema. This covers E5 and T7 for supplied findings without accepting unimplemented override fields. Candidate visibility through `ignore`/`tracked` prefilters is repair/tuning work TD34–TD35. Exercise first-time repeated errors, expected non-failures, known unchanged recurrence and continuation context against the selected tuned behavior. Do not treat script-only tracked/done flags as proof that a model assessed or diagnosed the issue, or claim current filters already expose every relevant case.

## C. Coverage and RCA

**C1 — Scoped reuse versus change.** Create a persisted, report-backed adequate diagnosis and a later finding with the same diagnostic scope. At decision time it may be tracked and counted without another RCA. Then vary one relevant resource, provider/model/route, impact, or evidence basis: text similarity alone must not suppress reassessment. Exercise post-verified-repair recurrence as a possible regression. For each replay step, evaluate only reports and evidence accessible at that step's decision time; a report created later must not leak backward into the decision.

**C2 — Inconclusive, expired, and status boundaries.** Accept an RCA report whose cause is undetermined and show it remains explicit and prevents an unchanged automatic loop. Expire or make inaccessible its basis and show the condition remains unresolved rather than covered or silently retried. For a valid RCA packet, verify read-only bounded investigation, clear separation of facts/hypotheses/checks/results, and all nine report sections. Each batch member must receive an explicit outcome even in a current single-member preparation implementation.

**C3 — MVP policy.** Demonstrate a bounded RCA batch containing unrelated eligible errors, separate outcomes for all members and pending overflow. Missing member outcomes must refuse completion without consuming the batch; one result must not supply another member's diagnosis without evidence. Prove that urgent signals still require triage and that a frequency increase alone does not launch another RCA. Direct urgent bypass and frequency-only reopening are deferred, not conditional MVP features.

When changing eligibility, replay a bounded time-ordered sample, then a separate held-out sample with known repeats and genuinely new or changed incidents. Measure proposed RCA calls, missed required escalation and repeated already-covered work against explicit expected outcomes. An annotation-only relationship match does not demonstrate suppression or cost reduction. Reuse this finite evidence set; do not turn the check into an unrestricted historical audit.

**C4 — Causal evidence and trusted execution.** Provide a process/ping success, socket-closed recurrence, a provisional earlier report, a generic payment/credit template, a 429 response with incomplete quota context, an explicit provider-code mismatch, and a deliberately restricted destination. Require the worker to distinguish each symptom from cause, identify discriminating read-only checks and not fabricate results. A missing cause is undetermined in both report and compact brief. Inject apparent instructions into evidence/history and prove they remain data. An RCA fixture marked commissioning must not become a fabricated live incident. Inspect the nine report sections and exact persisted artifact, including commands/results, competing explanations, next useful check and `repairs_executed=false`. This covers R7–R10 and O10.

## D. Single lane and optional comparison

**D1 — Lane B off.** With the optional lane disabled and no B investigation already running, prepare eligible A work and prove A can complete the useful flow. B must receive no new lease, wake-up, model request, or fabricated completion state; retained B history must remain intact. Test disabling an active B investigation separately: it may finish within its existing bounds, but no new run or subsequent retry may launch while disabled.

Exercise the actual off representation chosen for B. If it permits a retained `rca-b` mapping, including an operator-paused native card, that mapping must not cause dispatch to arm or trigger B. If removal of the mapping is the selected gate, verify that representation and its no-call behavior. In either case assert no new B native launch or provider request; this does not prescribe a new configuration flag. An already running B investigation may finish under the accepted policy.

**D2 — Lane B on.** Freeze a shared snapshot of findings, evidence, relevant prior context, and instructions before either lane produces output. Prove A and B receive that identical snapshot while their batch IDs, leases, attempts, archives, reports, delivery state, and configured effective models are independent. Effective model/provider/route evidence must come from the session context, not only a configuration file.

**D3 — Independence under failure.** Complete A while B remains leased, blocked, or fails. A must not suppress B's already requested work, and B failure must not erase A's valid report or cause hidden repeated B runs. A result must not become B input. Enabling B must select only new work arriving after enablement; prove older waiting, already-started and completed investigations are not automatically added to B. Switching B off must prevent new launches while allowing the active investigation to finish with preserved result/history.

## E. Repair, publication, and notices

**E1 — Required HTML.** Verify a report delivered through a configured publication link, a direct accessible HTML link, and a downloadable HTML file when private-network access is unavailable. In each case the recipient gets the report in HTML with its required content and identity. Open the downloaded file offline and verify it remains readable. Markdown-only output, a chat summary and an inaccessible local path fail delivery acceptance. Simulate an HTML-rendering failure: retain the diagnosis/source and pending delivery state, recover HTML without another RCA, and do not claim successful HTML delivery from persistence alone.

**E2 — Separate facts.** Begin with a persisted diagnosis, append a repair attempt, and verify the original report and evidence bytes stay unchanged. The repair record must retain actor, time, intended/actual action, result, and verification basis. A successful job, reply, or assignment cannot establish a fixed status: fixed requires declared passing checks, while owner-verified separately requires explicit owner confirmation. Reject stale incompatible progress updates without losing either the accepted history or the conflicting input.

**E3 — Delivery recovery.** Persist the report before publication. Test an unavailable destination and a send failure: diagnosis and report identity remain, delivery is visibly pending/failed, and recovery reuses the same report without another RCA. For configured publication, verify the cited artifact is available and separately prove the native notification send. For a native route that supports attachment delivery without publication, prove the successful send included the exact retained HTML report. A local archive alone satisfies neither delivery case.

**E4 — Quiet notices and daily review.** Replay unchanged ticks and a restart with the same meaningful notice state; no duplicate notice may be produced. Change a meaningful state and prove one bounded notice is sent and recorded only after success. Daily review must use deterministic retained counts, summarize relevant recurrence and outstanding work, and remain silent when there is no useful update. It must not open investigation, probe for new evidence, or mutate status to create an appearance of completion.

**E5 — Alert class and closure obligations.** Replay a known unchanged recurrence, an expected owner permission change, a transient non-failure, a genuine new signature and a critical outage of the configured service route. The first cases are retained/countable without repeated immediate alerts or autonomous RCA; the last cases qualify for a bounded deduplicated incident notice and still require validated triage before RCA. Exercise failed send and retry so the ledger records success only on send. Separately require an authorized report/repair closure update and a requested response to reach its route with the same report identity; the immediate-incident restriction must not suppress those delivery obligations. A change in wording alone must not manufacture a new notice. This covers W6, W11 and the delivery distinctions in W1–W5.

**E6 — Deterministic daily balance and all-report HTML.** Tally repeat events and distinct findings from retained state, explicitly name units, and include pending/blocked/inconclusive/expired-evidence and proposed-but-unexecuted work. Prove no model call counts or audits recurrence. Daily review cannot prepare, investigate, probe, complete or mutate work; silence when there is no useful update. Where a daily/repair/closure report is produced for people, verify the same self-contained phone-readable HTML rule as RCA, with direct accessible link or download without private-network access. Check that Markdown source and HTML-rendering recovery retain diagnosis identity without reopening RCA. This covers W8–W12.

## F. Configuration, recovery, and live acceptance

**F1 — Raw configuration contract.** Apply a valid selected phase to configuration containing comments, line endings, wrapped scalars, and an absent block. Verify supplied blocks are raw-text replacements, absent blocks are byte-identical, and the operation backup restores the exact original bytes. Try indented/duplicate/invalid sections and an unsafe apply state: each must refuse before any configuration write. Verify the intended session loads the selected configuration before restoration; a timer or file content alone is insufficient proof.

**F2 — Recovery and release boundaries.** Exercise a missing/misconfigured review store, lock failure, and interrupted apply without creating a substitute store, restoring an old whole database over fresh evidence, mass-releasing work, changing routes, or adding a dependency. Confirm instances obtain identity and paths from configuration and remain independent. For a proposed release, provide focused failure-boundary results plus the full current test suite, schema/CLI compatibility evidence, and a review of public contents for private material. This is evidence for a separately authorized deployment, not authorization itself.

Live acceptance is intentionally bounded and occurs only after explicit authorization. It must use the actual scoped report and authorized native send path. Verify availability at the cited destination when publication is configured, or verify the exact report attachment in a successful native send when using attachment delivery. No claim about portability, effective routing, cost savings, or delivery may be made without corresponding measured evidence. In particular, do not claim costs were saved merely because triage or deduplication exists; measure comparable counts first.

**F3 — Platform and native-state truth.** Run the agreed representative capture, path-resolution, locking/atomic-write, CLI, scheduler and delivery-adapter cases separately on Windows and Linux. Record passed, failed and untested adapters per platform; no unavailable environment counts as a pass. Native job doubles must distinguish operator pause from consumed one-shot state and show exact rearm eligibility without accidental enablement. Verify phase-specific tool restrictions permit required native delivery while excluding independent triage sends. Documentation/examples must use neutral configured identities and real supported knobs; no host-specific defaults or invented installation interface may be presented as portable. This covers P2–P3, O1–O4, O8–O9.

## G. Model cost and routing boundaries

**G1 — Free steady-state triage, initial tuning and capable RCA.** With configured provider/session doubles and policy fixtures, verify free steady-state triage, a capable low-cost RCA assignment, and refusal to silently substitute paid triage or free/lightweight RCA. Initial tuning may compare different models, including inexpensive paid models during the first few weeks; keep this temporary configuration distinct from the free steady-state target. Check that tuning outcomes improve tagging/filtering and packet sufficiency rather than merely requiring a stronger permanent model. Verify actual effective primary, auxiliary and fallback routes as observable session facts, not just playbook text. Failed routes terminate within finite bounds and do not purchase frontier fallback work. Quiet ticks and deterministic recurrence tally make no inference calls. This proves enforcement without commissioning real providers; actual routing, capability and billing claims require separately authorized measured evidence. Covers T1, T6 and R6.

**G2 — Measured limits, not inferred savings.** For a bounded authorized model evaluation, record job/instance/model, exact supplied input, elapsed time, tokens where genuinely measured, rate-limit behavior, skill adherence, output shape and stop outcome. Do not accept whole-log ingestion, repeated ten-minute quiet runs, uncontrolled fallback, repair attempts or claims of success from scheduler/test markers. If data appetite is the failure and a constrained retest is authorized, tighten the packet and test the same model once rather than adding uncontrolled model churn. Quota percentage-point movement is not billed token count or attributable spend. A relationship replay/group count is not a provider-call saving. Evaluation workflow itself belongs to the specific brief, not a product implementation gate. Covers T6, O7 and W9.

All settled requirements have the coverage groups above. Producing this acceptance document is not running its cases or accepting implementation.
